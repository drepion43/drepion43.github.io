## 들어가며

이전 글에서는 [Claude Code 설치 방법](2026-08-01-ClaudeCode_Install)을 다뤘습니다. 이번 글에서는 한 단계 더 들어가서, Claude Code가 터미널에서 "이 버그 고쳐줘" 같은 한 줄 요청을 받았을 때 내부적으로 어떤 과정을 거쳐 파일을 읽고, 코드를 고치고, 테스트를 돌리는지를 다루겠습니다. 핵심은 **에이전트 루프(Agent Loop)** 라는 구조입니다.

## 왜 "에이전트"인가

일반적인 챗봇은 사용자의 질문에 텍스트로 답하고 끝납니다. 반면 Claude Code는 답변 텍스트만 생성하는 것이 아니라, 목표를 달성하기 위해 **행동(action)** 을 스스로 선택하고, 그 행동의 결과를 관찰(observe)한 뒤, 다음 행동을 다시 선택하는 과정을 반복합니다. 이 "관찰 → 판단 → 행동"의 반복 구조가 있어야 비로소 "에이전트"라고 부릅니다.

전통적인 소프트웨어는 개발자가 미리 정해놓은 분기(if/else, 워크플로우)를 따라 움직입니다. 반면 에이전트는 다음에 무엇을 할지를 매 순간 모델 스스로가 결정합니다. 이 차이가 에이전트 루프를 이해하는 데 가장 중요한 전제입니다.

## 에이전트 루프의 기본 골격

Claude Code의 동작을 단순화하면 아래와 같은 반복문으로 요약할 수 있습니다.

```
while (작업이 끝나지 않았다면):
    1. 지금까지의 대화 + 도구 실행 결과를 모델에게 전달
    2. 모델이 다음 행동을 결정한다
       - 텍스트로 답변하고 끝내거나
       - 도구(Tool)를 호출한다
    3. 도구 호출이라면 실제로 그 도구를 실행하고 결과를 관찰한다
    4. 실행 결과를 다시 대화 기록에 추가한다
    5. 1번으로 돌아간다
```

이를 조금 더 형식화하면, 시점 $t$에서의 상태를 다음과 같이 표현할 수 있습니다.

$$
s_t = (\text{context}_0, a_1, o_1, a_2, o_2, \dots, a_{t-1}, o_{t-1})
$$

여기서 $a_i$는 모델이 선택한 행동(도구 호출 또는 최종 응답), $o_i$는 그 행동에 대한 관찰(도구 실행 결과)입니다. 모델은 매 스텝마다 다음 행동을 확률적으로 선택합니다.

$$
a_t \sim \pi_\theta(a_t \mid s_t)
$$

$\pi_\theta$는 모델의 정책(policy)이고, 파라미터 $\theta$는 학습된 가중치입니다. 중요한 점은 이 정책이 매 스텝마다 **전체 히스토리 $s_t$를 다시 입력받아** 다음 행동을 새로 계산한다는 것입니다. 즉 별도의 "상태 머신"이나 "플래너"가 따로 존재하는 것이 아니라, 모델이 매번 처음부터 전체 맥락을 보고 다음 한 걸음을 결정합니다.

## 도구 호출(Tool Use)이 루프를 완성한다

에이전트 루프가 실질적으로 의미를 가지려면 모델이 "행동"을 실제 세계에 반영할 수단이 있어야 합니다. Claude Code에서는 이 수단이 **도구(Tool)** 입니다.

- `Read` — 파일 내용을 읽는다
- `Edit` / `Write` — 파일을 수정하거나 새로 만든다
- `Bash` — 셸 명령을 실행한다 (테스트 실행, git 명령 등)
- `Grep` / `Glob` — 코드베이스를 검색한다

모델은 텍스트를 생성하는 대신, 정해진 스키마(JSON)에 맞춰 "이 도구를 이 인자로 호출하고 싶다"는 요청을 출력합니다. Claude Code 클라이언트는 이 요청을 파싱해서 실제로 해당 도구를 실행하고, 그 결과(파일 내용, 명령어 출력, 에러 메시지 등)를 다시 모델에게 돌려줍니다.

여기서 핵심은, **모델은 도구를 직접 실행하지 못한다**는 점입니다. 모델은 어디까지나 "무엇을 실행해줘"라는 요청만 생성할 뿐이고, 실제 실행과 그 결과를 관찰 가능한 형태로 되돌려주는 것은 클라이언트(Claude Code 런타임)의 역할입니다. 이 분리 덕분에 사용자는 위험한 명령(파일 삭제, force push 등) 실행 전에 승인 절차를 둘 수 있습니다.

## 한 스텝을 자세히 들여다보기

실제로 "이 함수의 버그를 고쳐줘"라는 요청이 들어왔을 때 루프가 어떻게 진행되는지 단계별로 살펴보겠습니다.

### 1단계 — 컨텍스트 파악

모델은 아직 어떤 파일에 문제가 있는지 모릅니다. 첫 행동은 대개 `Grep`이나 `Glob`으로 관련 코드를 찾거나, 사용자가 언급한 파일을 `Read`로 여는 것입니다.

```
a_1 = Read("src/utils/parser.py")
o_1 = <파일 내용 전체>
```

### 2단계 — 원인 분석

받은 파일 내용을 바탕으로 모델은 다시 한번 전체 히스토리($s_2 = \text{context}_0 + a_1 + o_1$)를 입력받아 다음 행동을 결정합니다. 버그의 원인이 다른 파일에 있을 수도 있다고 판단하면 추가로 `Grep`을 호출할 수도 있고, 원인을 특정했다면 바로 `Edit`을 호출할 수도 있습니다.

### 3단계 — 수정 및 검증

```
a_2 = Edit("src/utils/parser.py", old_string=..., new_string=...)
o_2 = "File edited successfully"
a_3 = Bash("pytest tests/test_parser.py")
o_3 = <테스트 실행 결과>
```

테스트 결과가 실패라면 모델은 다시 원인을 분석하는 단계로 돌아갑니다(루프의 반복). 테스트가 통과하면 모델은 더 이상 도구를 호출하지 않고 텍스트로 결과를 요약하며 루프를 종료합니다.

### 종료 조건

루프는 다음 중 하나가 만족될 때 끝납니다.

- 모델이 도구 호출 없이 순수 텍스트 응답만 생성한 경우 (작업 완료로 판단)
- 사용자가 중간에 개입하여 중단한 경우
- 최대 스텝 수·토큰 한도에 도달한 경우

즉 루프의 종료는 외부에서 강제로 끊는 게 아니라, 대부분 **모델 스스로 "더 이상 도구가 필요 없다"고 판단하는 순간** 자연스럽게 끝난다는 점이 특징입니다.

## 컨텍스트 관리 문제

에이전트 루프가 길어질수록 $s_t$의 길이는 계속 늘어납니다. 파일 내용, 명령어 출력이 누적되면 결국 모델의 컨텍스트 윈도우(토큰 한도)를 넘기게 됩니다. Claude Code는 이를 해결하기 위해 몇 가지 전략을 사용합니다.

- **요약(Compaction)**: 대화가 길어지면 과거 히스토리를 압축된 요약으로 대체하고, 최근 히스토리만 원본 그대로 유지합니다.
- **서브에이전트(Subagent) 위임**: 탐색적이고 부피가 큰 작업(코드베이스 전체 검색 등)은 별도의 서브에이전트에게 맡기고, 메인 루프에는 그 결과 요약만 반영합니다. 이렇게 하면 메인 컨텍스트가 중간 탐색 과정으로 오염되지 않습니다.
- **선택적 파일 로딩**: 파일 전체를 매번 다시 읽지 않고, 필요한 범위(offset/limit)만 읽어 컨텍스트 낭비를 줄입니다.

이 문제는 본질적으로 $s_t$가 무한히 커질 수 없다는 제약과, 그럼에도 과거 행동의 근거를 잃으면 안 된다는 요구 사이의 트레이드오프입니다.

## 사람의 승인이 루프에 개입하는 지점

에이전트 루프는 완전 자율로 돌아갈 수도 있지만, Claude Code는 기본적으로 **위험도가 높은 행동 앞에서 사람의 승인을 기다리는 지점**을 둡니다. 즉 루프의 3단계("도구 실행")가 무조건 자동으로 일어나는 것이 아니라, 다음과 같이 나뉩니다.

$$
a_t \rightarrow
\begin{cases}
\text{자동 실행} & \text{(읽기 전용, 안전한 행동)} \\
\text{사용자 승인 대기 후 실행} & \text{(파일 수정, 셸 명령 등)}
\end{cases}
$$

사용자가 승인을 거부하면 그 거부 자체가 새로운 관찰 $o_t$로 히스토리에 추가되고, 모델은 이를 반영해 다른 접근을 시도합니다. 이 승인 메커니즘 덕분에 에이전트 루프는 "빠르게 반복하되, 되돌리기 어려운 행동에는 브레이크가 걸리는" 구조가 됩니다.

## 정리

Claude Code의 동작 원리를 한 문장으로 요약하면, **"모델이 전체 히스토리를 보고 다음 행동을 고르고, 그 행동을 도구로 실행한 결과를 다시 히스토리에 더해 반복하는 루프"** 입니다. 이 루프가 특별한 이유는 다음과 같습니다.

- 미리 정해진 워크플로우가 아니라 모델이 매 스텝 스스로 다음 행동을 결정한다.
- 도구 호출과 실행 결과 관찰이라는 피드백 루프를 통해, 한 번의 응답으로 끝나지 않고 목표를 달성할 때까지 반복한다.
- 컨텍스트가 무한히 커질 수 없다는 제약 때문에 요약·서브에이전트 위임 같은 컨텍스트 관리 전략이 함께 필요하다.
- 되돌리기 어려운 행동 앞에서는 사람의 승인이라는 개입 지점을 둔다.

결국 "에이전트답다"는 것은 화려한 프롬프트 엔지니어링이 아니라, 이 관찰-판단-행동 루프를 얼마나 견고하게 설계하느냐의 문제라고 할 수 있습니다.
