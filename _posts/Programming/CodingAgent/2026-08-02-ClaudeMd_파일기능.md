## 들어가며

앞서 [설치 방법](2026-08-01-ClaudeCode_Install), [동작 원리](2026-08-02-ClaudeCode_동작원리), [기능 정리](2026-08-02-ClaudeCode_기능) 글에서 Claude Code의 기본기를 다뤘습니다. 이번 글에서는 실제로 이 블로그 저장소에도 존재하는 `CLAUDE.md` 파일이 정확히 어떤 역할을 하는지, 그리고 어떻게 작성해야 효과적인지 정리하겠습니다.

## CLAUDE.md란

`CLAUDE.md`는 프로젝트 루트(또는 하위 디렉터리)에 두는 마크다운 파일로, Claude Code가 세션을 시작할 때 자동으로 읽어들여 **모델의 컨텍스트에 항상 포함시키는 프로젝트 설명서**입니다. 별도로 파일을 열어달라고 요청하지 않아도, Claude Code는 매 세션마다 이 파일의 내용을 시스템 프롬프트 성격으로 미리 로드합니다.

일반적인 코드베이스에는 `README.md`가 있지만, README는 "사람"을 대상으로 프로젝트를 소개하는 문서입니다. `CLAUDE.md`는 "에이전트"를 대상으로, 사람이 매번 반복 설명하기 귀찮은 규칙과 맥락을 미리 적어두는 문서라고 이해하면 됩니다.

## 왜 필요한가

모델은 기본적으로 프로젝트에 대한 사전 지식이 없습니다. 매 세션이 새로 시작될 때마다 다음과 같은 정보를 모른 채로 시작합니다.

- 이 프로젝트가 어떤 프레임워크/스택을 쓰는지
- 파일을 어디에 두어야 하는지, 네이밍 규칙은 무엇인지
- 빌드/테스트를 어떻게 실행하는지, 커밋 메시지 컨벤션은 무엇인지
- "이렇게는 하지 말아줘" 같은 팀 고유의 금기 사항

`CLAUDE.md`가 없다면 사용자는 매번 세션을 시작할 때마다 이런 맥락을 프롬프트로 다시 입력해야 합니다. `CLAUDE.md`에 적어두면 이 반복이 사라지고, 여러 세션·여러 사람이 같은 규칙을 공유하게 됩니다. 즉 `CLAUDE.md`는 **"매번 말하기 귀찮은 것을 한 번만 적어두는 곳"** 입니다.

## 어디에 둘 수 있는가

`CLAUDE.md`는 위치에 따라 적용 범위와 우선순위가 다릅니다.

- **프로젝트 루트**: 저장소를 여는 모든 사람/세션에 공통으로 적용됩니다. git으로 커밋해서 팀 전체가 공유하는 것이 일반적입니다.
- **하위 디렉터리**: 특정 하위 디렉터리 작업 시에만 추가로 로드되는 규칙을 둘 수 있습니다. 예를 들어 모노레포에서 `frontend/CLAUDE.md`, `backend/CLAUDE.md`처럼 영역별 규칙을 분리할 수 있습니다.
- **홈 디렉터리(`~/.claude/CLAUDE.md`)**: 특정 프로젝트에 국한되지 않고 사용자 개인이 항상 지키고 싶은 습관(예: "커밋 전에는 항상 diff를 보여줘")을 전역으로 적용할 때 사용합니다.

여러 위치의 `CLAUDE.md`가 동시에 로드될 수 있으며, 이 경우 더 구체적인 범위(하위 디렉터리)의 내용이 우선 적용되는 방식으로 동작합니다.

## 무엇을 적어야 하는가

효과적인 `CLAUDE.md`는 코드를 읽으면 알 수 있는 내용을 나열하지 않습니다. 모델이 코드베이스를 스스로 파악할 수 있는 정보(파일 구조, 함수 시그니처 등)는 굳이 적을 필요가 없습니다. 대신 아래와 같이 **코드만 봐서는 알기 어려운 맥락**을 적는 것이 효과적입니다.

### 1. 구조/컨벤션

```markdown
## 디렉터리 구조

- API 라우트는 `src/routes/`에 두고, 파일명은 리소스명(복수형)을 따른다. 예: `src/routes/users.ts`
- DB 접근 로직은 라우트에 직접 쓰지 않고 `src/repositories/`에 분리한다.
```

파일을 어디에 만들어야 하는지, 계층을 어떻게 나누는지처럼 "규칙은 있지만 코드만 봐서는 유추하기 어려운" 정보입니다.

### 2. 빌드/테스트 명령어

```markdown
## 개발 명령어

- 로컬 서버 실행: `npm run dev`
- 테스트: `npm test` (단일 파일: `npm test -- <파일경로>`)
- 린트: `npm run lint`
- 커밋 전 반드시 `npm run lint`와 `npm test`를 통과시킨다.
```

에이전트가 코드를 고친 뒤 스스로 검증할 수 있으려면, 정확한 명령어를 알아야 합니다. 이 정보가 없으면 모델이 `package.json`을 뒤져 추측해야 하므로 시간이 더 걸리고 틀릴 수도 있습니다.

### 3. 하지 말아야 할 것

```markdown
## 제약 사항

- `main` 브랜치에 직접 커밋하지 않는다. 항상 새 브랜치를 만들고 PR을 연다.
- 마이그레이션 파일은 생성만 하고, `db migrate`는 사용자가 직접 실행한다.
- 외부에 공개되는 API 응답 스키마는 사전 협의 없이 변경하지 않는다.
```

모델은 기본적으로 작업을 끝까지 완수하려는 경향이 있기 때문에, 이런 제약이 없으면 위험하거나 되돌리기 어려운 행동(강제 push, 프로덕션 마이그레이션 실행 등)까지 시도할 수 있습니다. 실수로 자동화되면 곤란한 행동은 명시적으로 금지해두는 것이 중요합니다.

## 작성 가이드

`CLAUDE.md`를 처음 쓸 때 막막하다면, 아래 순서로 접근하는 것을 권장합니다.

### 1단계 — `/init`으로 초안 생성

처음부터 백지에서 쓰기보다, Claude Code 세션에서 `/init` 커맨드를 실행하면 프로젝트를 스캔해서 구조·스택·주요 명령어를 파악한 초안을 자동으로 만들어줍니다. 이 초안을 베이스로 다듬는 것이 훨씬 효율적입니다.

### 2단계 — "내가 매번 설명하는 것"을 목록화

새 세션을 열 때마다 반복해서 알려주는 내용이 있다면, 그것이 `CLAUDE.md`에 들어가야 할 1순위 후보입니다. 예를 들어 세션마다 "테스트는 `pytest -x`로 돌려줘", "API 응답은 항상 snake_case로" 같은 말을 반복하고 있다면 바로 문서화 대상입니다.

### 3단계 — 실수했던 경험을 규칙으로 전환

과거 세션에서 모델이 원치 않는 행동을 했다면(예: 요청하지 않았는데 `git push`까지 실행, 테스트 없이 기능 추가 등), 그 경험을 구체적인 금지 규칙으로 적습니다. 추상적으로 "조심해서 작업해줘"라고 적는 것보다, "이런 상황에서는 이렇게 하지 마라"처럼 구체적인 사례 기반으로 적을수록 효과가 좋습니다.

### 4단계 — 짧게 유지하고 주기적으로 정리

```markdown
## Bad 예시 (너무 장황함)
이 프로젝트는 React 18과 TypeScript를 사용하며, 함수형 컴포넌트를 사용하고,
훅을 활용하며, 상태 관리는 Redux Toolkit을 사용하고, 스타일링은 styled-components를
사용하며... (이하 생략)

## Good 예시 (핵심만)
- Stack: React 18 + TypeScript, 상태 관리는 Redux Toolkit, 스타일은 styled-components
- 클래스 컴포넌트 대신 함수형 컴포넌트 + 훅만 사용
```

`CLAUDE.md`는 매 세션 컨텍스트에 항상 포함되므로, 불필요하게 길면 정작 중요한 규칙이 묻히고 토큰도 낭비됩니다. 문장으로 풀어쓰기보다 목록·표·코드블록으로 압축해서 적는 것이 모델 입장에서도 파싱하기 쉽고, 사람이 다시 읽을 때도 유지보수하기 좋습니다.

## 작성 시 주의할 점

- **너무 길게 쓰지 않기**: 위 4단계에서 설명한 대로, 장황한 설명보다 핵심 목록이 낫습니다.
- **최신 상태 유지**: 프로젝트 구조가 바뀌었는데 `CLAUDE.md`가 갱신되지 않으면, 모델이 오히려 틀린 정보를 신뢰하게 되는 역효과가 납니다. 리팩터링이나 스택 변경 시 `CLAUDE.md`도 함께 갱신하는 습관이 필요합니다.
- **코드로 알 수 있는 내용은 생략**: 함수 목록, 파일 트리처럼 모델이 직접 탐색해서 알아낼 수 있는 정보는 적지 않는 것이 좋습니다. 적어봐야 코드가 바뀌면 바로 낡은 정보가 됩니다.
- **명령형으로 명확하게**: "가능하면 테스트를 작성하는 게 좋을 것 같습니다" 같은 완곡한 문장보다 "새 함수를 추가하면 반드시 테스트를 작성한다"처럼 명확한 지시문으로 적는 것이 모델의 준수율을 높입니다.

## 정리

`CLAUDE.md`는 Claude Code가 세션 시작 시 자동으로 읽어들이는 프로젝트 전용 컨텍스트 파일로, README가 사람을 향한 문서라면 `CLAUDE.md`는 에이전트를 향한 문서입니다. 프로젝트 루트/하위 디렉터리/홈 디렉터리에 각각 다른 범위로 둘 수 있고, 코드만 봐서는 알기 어려운 구조·명령어·제약 사항을 적어두는 것이 핵심입니다. 작성할 때는 `/init`으로 초안을 만든 뒤, 반복 설명하던 내용과 과거 실수 경험을 구체적인 규칙으로 옮기고, 장황한 설명 대신 짧고 명확한 목록으로 정리하는 것이 가장 효과적인 접근입니다.
