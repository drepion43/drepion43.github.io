## 들어가며

앞서 <a href="https://drepion43.github.io/codingagent/ClaudeCode_기능/" target="_blank">기본/커스텀 커맨드</a>와 [CLAUDE.md]<a href="https://drepion43.github.io/codingagent/ClaudeCode_파일기능/" target="_blank">CLAUDE.md</a>를 다뤘습니다. 이번 글에서는 그와 비슷해 보이지만 성격이 다른 **Skills(스킬)** 기능을 정리하겠습니다. 커스텀 커맨드가 "사용자가 직접 호출하는 프롬프트 단축키"라면, Skills는 "모델이 상황에 맞게 스스로 꺼내 쓰는 절차서"에 가깝습니다.

## Skills란

Skill은 특정 작업(예: 엑셀 보고서 생성, PDF 양식 채우기, 특정 리뷰 체크리스트 수행)을 수행하는 방법을 정리해둔 **패키지화된 지침 모음**입니다. 한 개의 스킬은 폴더 하나로 구성되며, 그 안에 `SKILL.md`라는 파일과 필요하다면 스크립트, 템플릿, 참고 문서 등을 함께 둘 수 있습니다.

```
.claude/skills/
  weekly-report/
    SKILL.md
    template.xlsx
    generate_summary.py
```

`SKILL.md`는 다음과 같은 구조를 가집니다.

```markdown
---
name: weekly-report
description: 팀 주간 업무 보고서를 정해진 엑셀 템플릿 형식으로 생성한다. 사용자가 "주간 보고서 작성해줘", "이번 주 리포트 정리해줘"라고 요청할 때 사용한다.
---

1. `template.xlsx`를 열어 이번 주 날짜에 맞는 시트를 확인한다.
2. git log와 이슈 트래커에서 이번 주 완료 항목을 수집한다.
3. `generate_summary.py`를 실행해 요약을 만든 뒤, 템플릿의 정해진 셀에 채워 넣는다.
4. 완료되면 파일 경로를 사용자에게 알려준다.
```

## 커스텀 커맨드와 무엇이 다른가

커스텀 커맨드와 Skills는 둘 다 "반복 작업을 재사용 가능하게 만든다"는 목적은 같지만, 호출되는 방식과 쓰임새가 다릅니다.

| 구분 | 커스텀 커맨드 | Skills |
|---|---|---|
| 호출 방식 | 사용자가 `/커맨드이름`으로 명시적으로 호출 | 모델이 작업 맥락을 보고 관련성이 있으면 스스로 판단해서 사용(명시적 호출도 가능) |
| 구성 | 마크다운 파일 1개(프롬프트 템플릿) | 폴더 단위. 지침 + 스크립트 + 템플릿 등 여러 파일을 함께 번들링 |
| 컨텍스트 로딩 | 호출 시 전체 내용이 그대로 프롬프트에 삽입 | 평소에는 `name`/`description`만 가볍게 로드되고, 실제로 관련 작업이 감지될 때만 본문 전체를 불러옴(progressive disclosure) |
| 적합한 용도 | 짧고 정해진 프롬프트를 빠르게 재사용 | 여러 단계·여러 파일이 필요한 절차형 작업, 재사용 가능한 도메인 지식 |

가장 큰 차이는 **로딩 방식**입니다. 커스텀 커맨드는 사용자가 호출하는 순간 전체 프롬프트가 컨텍스트에 들어갑니다. 반면 Skills는 세션 시작 시 모든 스킬의 `description`만 가볍게 읽어두고, 실제 작업이 그 설명과 관련 있다고 판단될 때만 `SKILL.md` 본문과 첨부 파일을 불러옵니다. 스킬이 아무리 많아도 평소 컨텍스트 사용량에는 거의 영향을 주지 않는 구조입니다.

## 왜 필요한가

같은 절차형 작업을 CLAUDE.md에 다 적어두면 될 것 같지만, 두 가지 문제가 있습니다.

1. **컨텍스트 낭비**: CLAUDE.md는 항상 전체가 로드됩니다. 자주 쓰지 않는 특수 작업(분기별 감사 리포트 생성 등)까지 CLAUDE.md에 다 적으면, 정작 필요 없는 세션에서도 매번 그 내용을 읽어야 합니다.
2. **파일 번들링 불가**: CLAUDE.md는 텍스트 지침만 담을 수 있지만, 실제 작업은 스크립트나 템플릿 파일이 함께 필요한 경우가 많습니다. Skills는 폴더 구조이기 때문에 지침과 실행 파일을 한 세트로 묶을 수 있습니다.

즉 CLAUDE.md는 "이 프로젝트에서 항상 알아야 할 것", Skills는 "특정 작업이 필요할 때만 꺼내 쓰는 전문 지식"으로 역할이 나뉩니다.

## 저장 위치

- **프로젝트 스킬**: `.claude/skills/<스킬이름>/` — 저장소에 커밋하면 팀 전체가 공유합니다.
- **개인 스킬**: `~/.claude/skills/<스킬이름>/` — 모든 프로젝트에서 나만 사용합니다.
- **플러그인 스킬**: 플러그인 형태로 배포되어 여러 조직/팀에 공유되기도 합니다.

## Skills 작성 가이드

### 1. description을 구체적이고 트리거 중심으로 쓴다

모델은 평소 `description`만 보고 "지금 이 스킬을 쓸지 말지"를 판단합니다. 따라서 description은 무엇을 하는지뿐 아니라 **언제 사용해야 하는지**까지 명시해야 합니다.

```markdown
# Bad
description: 보고서를 만든다

# Good
description: 팀 주간 업무 보고서를 정해진 엑셀 템플릿 형식으로 생성한다. 사용자가 "주간 보고서 작성해줘", "이번 주 리포트 정리해줘"라고 요청할 때 사용한다.
```

Bad 예시는 너무 추상적이라, 모델이 다른 "보고서" 관련 요청과 헷갈릴 수 있습니다. Good 예시는 구체적 트리거 문구까지 담고 있어 관련성 판단이 쉬워집니다.

### 2. 본문은 절차를 단계별로 명확히 쓴다

스킬 본문은 설명문보다 체크리스트/번호 목록 형태가 낫습니다. 모델이 실행 중 놓치는 단계 없이 그대로 따라갈 수 있기 때문입니다.

```markdown
1. `data/raw/`에서 최신 CSV 파일을 찾는다.
2. `scripts/validate.py`로 스키마를 검증한다. 실패하면 사용자에게 어떤 컬럼이 문제인지 보고하고 중단한다.
3. 검증을 통과하면 `scripts/transform.py`로 변환한 뒤 `data/processed/`에 저장한다.
```

### 3. 반복 실행 로직은 스크립트로 분리한다

매번 모델이 코드를 새로 작성하게 하는 것보다, 검증된 스크립트를 스킬 폴더에 함께 두고 실행만 하도록 지시하는 편이 훨씬 안정적입니다. 예를 들어 데이터 검증 로직처럼 정확성이 중요한 부분은 `SKILL.md`에 "이렇게 검증해줘"라고 자연어로 풀어쓰기보다, `validate.py` 스크립트를 두고 "이 스크립트를 실행해서 검증한다"고 지시하는 것이 결과의 일관성을 높입니다.

### 4. 스킬 범위를 좁게 유지한다

하나의 스킬에 너무 많은 작업을 몰아넣으면 description이 애매해지고, 모델이 언제 사용해야 할지 판단하기 어려워집니다. "주간 보고서 생성"과 "월간 감사 리포트 생성"처럼 트리거 조건과 절차가 다르다면 스킬을 분리하는 것이 좋습니다.

### 5. 사람이 검토할 수 있는 형태로 유지한다

스킬은 결국 팀이 공유하는 "표준 작업 절차서"이므로, 코드 리뷰하듯 PR로 추가/수정하고, 실제 절차가 바뀌면 스킬도 함께 갱신해야 합니다. 오래된 스킬은 CLAUDE.md와 마찬가지로 모델을 잘못된 방향으로 이끄는 원인이 됩니다.

## 정리

Skills는 폴더 단위로 지침·스크립트·템플릿을 함께 묶어두고, 평소에는 `description`만 가볍게 로드했다가 실제로 관련 작업이 감지될 때만 전체 내용을 불러오는 기능입니다. 사용자가 명시적으로 호출하는 커스텀 커맨드와 달리, 모델이 작업 맥락에 맞춰 스스로 판단해 사용한다는 점이 가장 큰 차이입니다. 좋은 스킬을 만들려면 description을 트리거 중심으로 구체적으로 쓰고, 본문은 단계별 절차로 정리하고, 반복되는 실행 로직은 스크립트로 분리하며, 스킬 하나의 범위는 좁게 유지하는 것이 핵심입니다.
